# Live Dashboard 设计文档

定位：**以公演为中心、从官方来源提取重要信息的观演 Dashboard**，而不是把两个官网装进 WebView。

核心结构：

**官方发布页 → 服务端提取与核验 → 统一公演数据库 → SwiftUI 原生卡片界面。**

首页的一张卡片代表一项公演；进入后，始终围绕当前选择的日期／场次，展示对应的票务、座位和物贩信息。用户可以配置哪些信息卡片显示、顺序、详细程度，以及哪些变化需要提醒。

已核实官方入口、部分页面分区、通贩页面正文及店铺迁移关系。部分演出官网正文在研究环境中返回了 403／404；因此涉及这些页面的 DOM 提取规则是**实施方案，需要用实际可访问的 HTML 快照验证**，不是已经跑通的爬虫。

# 一、官方信息源应该接入哪些网站

## 1. BanG Dream!

| 官方入口 | 作用 | App 的使用方式 |
|---|---|---|
| [BanG Dream! Live／Event 列表](https://bang-dream.com/events/) | 官方演出与活动发现入口，列表可以按团体等条件分类。 | 发现新公演、读取列表摘要，再进入详情页。 |
| [官方公演详情示例：MyGO!!!!! × Ave Mujica](https://bang-dream.com/events/mygo-avemujica2026/) | 单场公演的名称、日期、票价与受付信息。 | 作为公演主来源；将不同票种、不同轮次分别提取。 |
| [Bushiroad 官方通贩：Live 商品列表](https://bushiroad-store.com/blogs/live) | 按演出组织的通贩文章，包含分页。 | 发现与公演关联的通贩批次，再追踪商品／购买页面。 |

**不能只读取 `/events/` 下的页面。**例如，BanG Dream! 的周年公演相关区域、物贩及现场活动说明也可能放在独立专题路径里，而且一个专题页可能同时关联几项公演。它应该成为这些公演的共同资料来源，而不是被误识别成一项新 Live。

**也不能把 Bushiroad 商店中的所有内容都归入 BanG Dream! Live。**它的 Live 商品列表同时包含其他企划及艺人个人演出的商品，因此需要通过官方关联链接、公演身份和人工确认进行筛选。

## 2. Love Live!

Love Live! 采用“**系列主站＋各分支 Live 列表＋跨系列特设页**”的发现方式，不只监控一个页面。

| 官方入口 | 作用 |
|---|---|
| [系列主站](https://www.lovelive-anime.jp/)／[官方新闻](https://www.lovelive-anime.jp/news/) | 新公演发布、追加信息、变更公告的总入口。 |
| [Aqours Live 列表](https://www.lovelive-anime.jp/uranohoshi/live.php) | Aqours 分支演出入口。 |
| [虹咲 Live 列表](https://www.lovelive-anime.jp/nijigasaki/live.php) | 虹咲分支演出入口。 |
| [Liella! Live 列表](https://www.lovelive-anime.jp/yuigaoka/live/) | Liella! 分支演出入口。 |
| [莲之空 Live／Event 列表](https://www.lovelive-anime.jp/hasunosora/live-event/) | 莲之空分支公演及活动入口。 |
| [イキヅライブ！Live／Event](https://www.lovelive-anime.jp/lovehigh/live/) | LOVELIVE! BLUEBIRD 分支入口。 |
| [跨系列公演详情示例：15 周年 Love Live! Fes](https://www.lovelive-anime.jp/special/live/live_detail.php?p=15th_lovelivefest) | 特设页中有公演概要、票务、申请、Goods、海外观众等分区。 |

实际核实到、会直接影响爬虫设计的情况：

**官方通贩门户的 LIVE GOODS 链接仍会经过旧站，而旧站会显示迁移公告，再指向 `lovelive.fannect.jp`。**所以必须保存来源的迁移／别名关系，不能将旧地址出现维护页简单解释为“通贩结束”。

第一版的内容范围限定为**这两个企划名义下的官方公演**。声优个人演唱会、一般商品发售、广播、动画播出等不自动进入首页；Fan Meeting、上映会等则作为可选活动类型，默认与 Live 分开。

# 二、根据实际页面，应该怎样提取数据

## 1. 不要使用“一套正则扫描整页”

MyGO!!!!! 9th Live 通贩文章中，页面顶部同时存在其他商品、其他活动的截止提示；文章自己的标题、发布日期和图片则位于正文区域。**直接扫描整页所有日期，会把别的活动截止时间错误归给这场 Live。**

正确的提取顺序：

```text
识别来源与页面模板
    ↓
定位公演／文章主内容区域
    ↓
排除全站导航、广告、页脚、其他活动推荐
    ↓
按标题及相邻内容拆分区块
    ↓
提取区块内的日期、金额、链接、图片
    ↓
确定这些信息适用于哪一项公演、哪一天、哪个轮次
    ↓
校验后发布
```

页面存在公开结构化数据时，可以优先利用，但仍需与可见正文核对。**没有确认可长期依赖的官方公开演出 API，不应将某个未核实的隐藏接口作为整个 App 的基础。**

## 2. 两家官网需要不同的解析适配器

### BanG Dream!：公演详情＋相关专题＋通贩文章

至少分成三个适配器：

| 适配器 | 主要工作 |
|---|---|
| `BangDreamEventIndexAdapter` | 从列表发现公演，获取详情链接、列表日期与团体标签。 |
| `BangDreamEventDetailAdapter` | 按公演概要、出演、票务、物贩、注意事项等区块提取正文。 |
| `BushiroadLiveGoodsAdapter` | 解析通贩列表和文章，发现商品链接、原图及销售批次。 |

列表标签可以辅助分类，但**不能仅因标题含有某位声优或某个团体名称，就自动认定为目标公演**。

### Love Live!：新式详情页＋旧式分页面＋官方新闻

新式特设页：

```text
live_detail.php?p=某个公演标识
```

历史公演也存在独立的 `sp_…_merch.php`、票务分页面。例如虹咲 5th Live 的物贩就是独立页面，而非只有一个详情页内部锚点。

适配器：

```text
LoveLiveIndexAdapter
LoveLiveDetailAdapter
LoveLiveLegacyPageAdapter
LoveLiveNewsAdapter
LoveLiveGoodsStoreAdapter
```

最重要的 URL 规则：**不能清除所有查询参数。**`p` 是公演身份的一部分；把它去掉会把不同公演错误合并。追踪参数可以清除，但需要白名单式保留有语义的参数。

## 3. 票务要提取“轮次”，不能只提取一个售票链接

每一轮受付都应该成为单独记录：

| 信息 | 应提取的内容 |
|---|---|
| 轮次身份 | 官方名称，例如先行抽选、一般发售、追加席、升级受付。 |
| 适用范围 | 哪一天、哪一场、哪些票种。 |
| 时间 | 申请开始／结束、结果公布、付款期限。 |
| 资格 | 会员、序列码、指定商品、已有基础票等前提。 |
| 价格关系 | 完整票价、升级差额、手续费、含税说明。 |
| 入口 | 官方公告链接、实际申请平台链接、海外专用入口。 |
| 状态依据 | 官方明确状态、按公告时间推算的状态、最后核对时间。 |

尤其要区分：

**“申请时间已开始”不等于“目前一定还有票”；“升级费用”不等于“完整票价”；“直播观看期限”不等于“现场公演日期”。**

首页不应把 U20、直播票或升级差额算进普通现场票的“最低价”。

## 4. Goods 必须以“销售批次”建模

School idol STORE 中，同一项 15 周年公演就有事前通贩和 After Pamphlet 等不同入口，受付与发货安排分别列出。它们应属于**同一场公演下的不同物贩批次**，不能相互覆盖。

BanG Dream! 的官方 Live 商品列表也存在同一大型公演按 DAY1、DAY2、DAY3 分开的通贩入口。商品资料需要能够关联到某一天，而不是全部无条件应用于整场活动。

三个维度分开：

| 维度 | 取值示例 |
|---|---|
| 购买渠道 | 网上购买、现场购买。 |
| 履约方式 | 邮寄、会场领取。 |
| 销售阶段 | 事前、会期、事后。 |

这样，“网上预订、当天会场领取”就不会被错误地强行塞进“纯通贩”或“纯场贩”中的某一个类别。

## 5. 图片需要作为正式数据保存

图片分别标记为：

**主视觉、商品一览表、场贩说明图、物贩区域图、公演座位图、场馆通用座位图。**

提取时检查正文中的图片、响应式图片候选、懒加载属性以及图片外层的原图链接，并结合附近标题和说明判断用途。属性检查是拟采用的规则，具体选择器仍需按实际 HTML 验证。

App 显示上：

- 默认展示完整图片，不把商品表、座位表裁成正方形。
- 支持点击后全屏放大，保留清晰版本与来源。
- 对图片内容变化进行检测，而不只检查 URL 是否变化。

有文字版时优先提取文字。只有图片确实承载唯一信息时，才考虑图中文字识别，并要求**价格、截止日期和限制条件经过核验后再进入结构化字段**；无法确认的部分仍展示原图，不自动补写。

# 三、核心数据模型：公演和“某一天”必须分开

```text
LiveEvent：一项官方公演／巡演
    ├── LiveStop：巡演站点，可选
    ├── Performance：具体日期与场次
    ├── TicketTier：票种
    ├── TicketRound：受付轮次
    ├── TicketOffer：轮次、票种、场次、价格与入口的关联
    ├── GoodsCampaign：物贩批次
    ├── MediaAsset：座位图、商品图、说明图
    └── Notice：变更、取消、退票等公告

SourceDocument / SourceEvidence：来源与字段证据
UserEventState / CardConfiguration：用户自己的状态和界面设置
```

## 关键模型职责

| 模型 | 需要保存的关键内容 |
|---|---|
| `LiveEvent` | 稳定 ID、官方全名、企划、团体、主要来源、整体状态。 |
| `Performance` | 稳定 ID、Day 标签、该场副标题、当地日期、开场／开演时间、会场、当场出演者。 |
| `TicketRound / TicketOffer` | 受付名称、时间、资格、票种价格、申请链接、适用场次。 |
| `GoodsCampaign` | 购买方式、销售／领取时间、发货说明、购买限制、适用范围、原图。 |
| `MediaAsset` | 图片用途、原图地址、缩略图、来源、公演／场次范围、版本。 |
| `SourceEvidence` | 来源 URL、支持该字段的原文、来源发布时间、成功核对时间、核验状态。 |
| `CardConfiguration` | 卡片类型、显示／隐藏、排序、密度、提醒、全局／公演级覆盖。 |

### 必须从第一版就落实的规则

**第一，场次 ID 不能由日期生成。**公演延期后，应保留原来的身份、关注状态和提醒配置，只更新日期。

**第二，共通信息和当天信息必须明确区分。**定义：

```text
整项公演共通
指定巡演站点
指定一个或多个场次
适用范围尚未确认
```

不能把“没有写 Day2”自动理解为“与 Day1 相同”。

**第三，同一天也可能有多场。**选择器最终选中的是 `Performance`，不是只有 `Date`；否则昼公演、夜公演会混在一起。

**第四，数据状态不能只有“有／无”。**至少区分：

> 已确认、官方明确待公布、尚未获取、解析失败、不适用。

“网站抓取失败”不能显示成“官方尚未公布”。

**第五，所有重要字段都要能回到官方来源。**来源的发布时间、最后成功核对时间、App 下载时间是三件不同的事。不能因为今天重新抓到一篇旧公告，就让它覆盖更新的信息。

# 四、App 的页面与交互设计

## 1. 底部只保留三个原生 Tab

**演出｜我的｜设置**

“演出”负责发现；“我的”负责关注、计划参加、申请记录和临近提醒；“设置”负责默认卡片、显示语言、时区、缓存等。更新动态放在“我的”里面。

## 2. 首页：一项公演一张卡片

首页采用纵向卡片流：

```text
┌─────────────────────────────┐
│ Love Live!              已关注 │
│ 公演官方名称                    │
│ 团体／该公演的参与企划             │
│                               │
│ 日期范围 · 共 2 场               │
│ 会场／城市                     │
│                               │
│ 当前：某轮受付进行中              │
│ 下一事项：申请截止时间             │
│                               │
│ Day1 · Day2        有重要更新     │
└─────────────────────────────┘
```

首页默认重要性：**公演身份 → 日期／会场 → 当前票务阶段 → 最近需要处理的事项。**

价格、物贩状态和缩略图可由用户决定是否显示。海报不应占掉大部分卡片面积。

筛选项包括企划、团体、日期范围、地区、活动类型，以及“只看关注”“只看有待办事项”。按团体筛选到多日公演时，应标明命中了哪一天。

同一公演多日合并；巡演在同一卡片下显示站点数量，并提供站点选择。**不能仅因为会场相同或名称相似，就合并两项官方上独立的公演。**

## 3. 详情页：名称最上方，场次选择控制全部内容

```text
返回                           关注  ⋯

公演官方完整名称
当前日期／场次副标题

[ 当前站点／日期／Day／昼夜场选择 ]

[ 概要 | 售票 | 座位 | 周边 ]

┌─────────────────────────────┐
│ 当前 Tab 的重要信息卡片        ⋯ │
│ ……                            │
└─────────────────────────────┘
```

公演名称使用多行完整显示。发生取消、延期等重大状态时，在标题区域显示状态提示，不依赖用户是否打开了某个 Tab。

| Tab | 卡片内容 |
|---|---|
| **概要** | 当前场次时间、地点、出演者、票价、入场关键条件。 |
| **售票** | 当前及即将开始的受付、申请资格、申请入口、结果／付款期限、过去轮次。 |
| **座位** | 本公演座位图、场馆通用图、席种说明；不同类型必须标识清楚。 |
| **周边** | 场贩、通贩、会场领取、商品表与现场规则图片。 |

### 多日切换规则

只有两三场时，使用原生分段选择器。场次数量较多时，使用原生菜单或弹出选择页，按“站点 → 日期 → 昼夜场”组织。

切换场次时，**四个 Tab 都必须使用同一个 `selectedPerformanceID`**。用户当前停留的 Tab 不变，但里面的价格、链接、座位图和场贩时段全部重新匹配。

共同信息显示“全日共通”；只对应 Day1 的信息，切换 Day2 后不应继续出现。范围尚未确定的资料显示在单独的“适用日期待确认”卡片中，不能悄悄当作共通资料。

## 4. 各 Tab 内部怎样“只保留重要信息”

### 概要

“时间与会场”“出演”“票价”“入场条件”四类卡片。

日期必须保留主办方所在地时区；用户可以额外开启本地时间显示。没有公布开演时间时，显示“开演时间待公布”，不要用日期零点代替。

价格按票种列明，升级差额、特典包含内容和手续费说明保留在对应票种下面。条件较长可以折叠，但购买前提不能被摘要省略。

### 售票

每个受付一张行动卡片：

```text
受付官方名称                       ⋯
适用：Day1／Day2
类型：抽选

申请期间：……
申请条件：……
结果公布：……
付款期限：……

[前往官方申请]   [提醒]
```

已经结束的轮次默认折叠。进行中与即将开始的轮次分开。

“我已申请”“我已付款”“我已有基础票”属于用户手动记录，不能从公开网页推断出来；它们可以决定个人提醒，但不能修改官方票务事实。

### 座位

明确区分：**本公演官方座位图**与**场馆通用座位图**。后者不等于这场公演的实际舞台或座席配置。只有通用图时，需要持续显示提示；不根据别的演唱会图片生成本场舞台布局。

### 周边

“现场”“通贩”两个分类入口，并将线上预订、会场领取清楚标记。

场贩卡片重点保留：日期和营业时段、位置、整理券／预约要求、是否必须持票、限购、付款方式、商品表和现场说明图。

通贩卡片重点保留：受付批次、截止时间、预计发货、官方是否明确预计演出前送达、配送限制、商品入口及图片。

**场贩时间可以早于公演日期；通贩时间也可以晚于公演结束。**界面必须按销售批次展示，不应强制套用开演日。

# 五、每张重要信息卡片如何设置

同时提供**全局默认设置**和**单项公演覆盖设置**。

| 设置项 | 行为 |
|---|---|
| 显示／隐藏 | 例如隐藏出演卡片，但保留票务与物贩。 |
| 排序／置顶 | 将最关心的信息移动到该 Tab 顶部。 |
| 紧凑／详细 | 只显示主要值，或展开次要说明。 |
| 字段选择 | 例如时间卡片是否显示当地时间和本地时间两列。 |
| 变化提醒 | 票务新增、座位图发布、场贩说明更新等。 |
| 截止提醒 | 为某个申请／购买期限设置提前提醒。 |
| 适用范围 | 仅当前公演，或作为同类卡片的默认配置。 |

操作入口采用卡片右上角原生 `Menu`；完整排序和显示设置放进原生 `List`／`Form` 编辑页。

用户调整后的顺序和隐藏状态不能因为官网更新而重置。配置应绑定**稳定卡片类型及对应实体 ID**，不能绑定数组下标。

取消、延期、退票等重大状态放在公演标题区，而不是依赖一张可能被隐藏的普通卡片。

# 六、原生 iOS 技术架构

## 1. UI 组件选择

**iOS 18+ 为第一版部署目标**，主体使用 SwiftUI，少量确有需要的功能桥接 UIKit。

| 功能 | 实现 |
|---|---|
| 底部导航 | `TabView`。 |
| 页面跳转 | `NavigationStack`。 |
| 首页卡片流 | `ScrollView`＋`LazyVStack`。 |
| 详情分区切换 | `Picker`＋`.segmented`。 |
| 多日期／多场次 | 简单场景 `Picker`；复杂场景 `Menu` 或选择 `sheet`。 |
| 卡片操作 | `Menu`、`Button`、`Toggle`。 |
| 排序设置 | `List`、`EditButton`、`.onMove`。 |
| 长说明 | `DisclosureGroup`。 |
| 设置页面 | `Form`、`Section`。 |
| 图片／PDF 放大 | 封装原生图片缩放视图；PDF 使用 PDFKit。 |

视觉上使用系统字体、语义颜色、原生导航和控件。卡片只负责内容分组。

购票和购买动作打开官方链接，让用户在官方流程中登录、支付。WebView 不承担 App 主界面，也不在 App 内收集票务账号密码。

## 2. 按功能组织，而不是一个巨大 ViewModel

```text
LiveDashboard/
├── App/
│   ├── LiveDashboardApp
│   ├── RootTabView
│   └── AppRouter
├── Features/
│   ├── Dashboard/
│   ├── LiveDetail/
│   │   ├── Overview/
│   │   ├── Tickets/
│   │   ├── Seating/
│   │   └── Goods/
│   ├── MyLives/
│   └── CardSettings/
├── Domain/
│   ├── Models/
│   ├── PerformanceScopeResolver
│   ├── TicketStatusResolver
│   └── ImportantInformationPolicy
├── Data/
│   ├── APIClient
│   ├── LiveRepository
│   ├── Persistence/
│   └── MediaCache/
└── Services/
    └── ReminderService
```

第一版一个 App target 足够。

视图状态使用 `@Observable` 模型与 SwiftUI 数据绑定；页面 Store 放在 `@MainActor`，网络、解码和数据转换与 UI 分离。

**View 负责显示；Store 负责页面状态；Repository 负责数据获取与缓存；Domain 负责场次匹配、状态推算及重要性判断。**

不要在 `body` 中解析日期、查找售票轮次、拼接来源关系。

## 3. 一次获取整项公演，切换日期时本地过滤

详情 API 一次返回该公演所有场次及关联记录。进入页面时先读取本地快照，再请求更新。Day1／Day2 切换不必每次请求网络，也能离线切换。

需要下载图片或补充内容时，请求必须与当前实体 ID 绑定，切换后取消不再需要的任务，并在返回时再次核对 ID。

## 4. 公共信息与个人设置分开保存

公共公演资料是可重新下载的缓存；关注、个人申请记录、卡片顺序、提醒设置则是用户数据，不能在清理缓存时一起删掉。

本地持久化使用 SwiftData。后续需要多设备同步时，可为用户数据配置兼容 CloudKit 的独立存储。**不要把整个公共演出库和全部图片放进每个用户的私人 iCloud。**

# 七、服务端更新、可靠性与提醒

## 1. 为什么需要服务端

iOS 没有保证应用持续后台执行、在任意指定时间执行、或按固定间隔运行的通用机制。不应设计成“App 每隔十分钟后台抓官网”。

```text
服务端定时发现与抓取
    ↓
保存来源快照
    ↓
解析候选数据
    ↓
字段校验／冲突审核
    ↓
发布一致的数据版本
    ↓
生成重要变更记录
    ↓
App 同步＋按用户设置发送提醒
```

第一版用小型采集服务、关系型数据库和简单审核界面。

## 2. 发布前的可靠性规则

**原始抓取结果不能直接覆盖线上资料。**

解析异常、模板变化、来源冲突、价格或时间异常时，应保留上一次确认的数据，并显示核对状态。抓取失败不代表公演取消，也不代表链接对应的受付已经结束。

保留每次来源快照和解析器版本；对外发布采用经过验证的整项公演版本。

“较晚抓到”也不是“较新公告”。来源优先级必须结合具体字段、公告内容和发布时间；明确的更正公告可能优先于未及时修改的详情页，无法确定时进入人工审核。

抓取频率从低频开始，对正在受付、接近开演的公演适当提高；遵守来源站点规则、限流与重试要求。遇到登录、验证码或访问限制，不将绕过它们作为采集方案。

## 3. 提醒分为两种

| 提醒类型 | 机制 |
|---|---|
| 已知时间的提醒 | 用户选择后，使用本地通知安排，例如申请截止前一天。 |
| 后来才出现的变化 | 服务端发现新轮次、时间变更或座位图后，再发送远程通知。 |

所有提醒应深链到**正确公演、正确场次、正确 Tab、正确卡片**。截止时间改变时，要替换旧提醒。

## 4. 图片和官方内容的使用方式需在发布前确定

可以浏览到图片，不等于自动取得重新托管或分发许可。App 上架前，需要核查站点条款、内容使用和品牌呈现方式。未经确认的资料可先保留摘要与官方入口，不默认批量重新托管。

App 名称与介绍应明确它是独立的信息整理工具，避免给人官方客户端的印象。

# 八、实施顺序与验收标准

## 实施顺序

| 阶段 | 交付内容 |
|---|---|
| **数据基础** | 官方来源登记、代表性页面快照、各模板解析器、统一模型、来源证据和审核流程。 |
| **核心 App** | 首页公演卡片、四个详情 Tab、多场次切换、完整物贩图片、卡片配置、关注及离线缓存。 |
| **追踪增强** | 重要变化记录、截止提醒、个人申请状态；随后再增加 iCloud 同步、日历和 Widget。 |

第一批测试样本应覆盖两家官网的新旧模板、两日公演、同日昼夜场、巡演、多个受付并行、共通物贩、单日物贩、线上预订会场领取，以及尚未公布座位图的情况。

## 必须通过的验收

| 测试场景 | 通过标准 |
|---|---|
| Day1 切换到 Day2 | 概要、价格、售票链接、座位和场贩范围全部一致切换。 |
| 同日昼夜场 | 开场／开演时间及出演者不会混用。 |
| 多轮受付同时存在 | 每轮时间、资格和价格关系独立，旧轮次不会覆盖新轮次。 |
| 一个通贩页关联多日 | 正确标记共通范围，不为每一天复制出互相冲突的数据。 |
| 旧网页或店铺迁移 | 保留身份与迁移关系，不误报公演消失或通贩结束。 |
| 抓取失败／字段缺失 | 保留确认数据，明确显示核对问题，不冒充“官方未公布”。 |
| 用户配置后更新数据 | 隐藏、排序、置顶和提醒设置不会重置。 |
| 图片更换但 URL 不变 | 能识别新版本，并更新对应图片卡片。 |
| 离线、重启、大字体 | 已缓存详情可读，选择状态合理恢复，文字和控件不被裁切。 |

**第一版最值得投入的是三件事：公演与场次身份稳定、每个字段有明确适用范围、所有重要信息可追溯到官方来源。**
